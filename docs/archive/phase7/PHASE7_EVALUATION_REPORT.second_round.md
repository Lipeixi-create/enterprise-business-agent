### A.3 `phase7-026` 失败根因

| 观察 | 数据 |
| --- | --- |
| 工具序列 | `query_metric(inventory_days, dimensions=[product])` → 重复的 `top_n(inventory_days, product, n=8)` |
| 重复性 | `query_metric` 已返回全部 8 个产品，`top_n n=8` 是同一指标、同一维度、同一周期的重复查询（`extra_tool_calls=1`） |
| LLM 调用 | 4 次：6.7 s ok / **61.6 s LLMTimeout** / 36.3 s ok / **15.2 s LLMTimeout** |
| 单例耗时 | 120.0 s（触顶） |
| 状态与判定 | `llm_timeout`、`passed=false`、`task_completion` + `number_accuracy` |
| 部分结论 | 保留两条工具证据原文，明确标注“分析未完成”“不可作为完整决策依据” |

直接原因不是单次调用慢，而是**单次逻辑调用含重试**：`llm_timeout=20 s` 且
`llm_max_retries=2`，一次逻辑调用最多可耗约 60 s。026 的两次超时合计约 77 s，
把 120 s 单例预算耗尽。

`number_accuracy=false` 属于部分结论的评分副作用：`26.713990` 确实出现在回答中，
但位于“首条值 26.713990，末条值 …”这一句，与指标词“库存天数”不在同一句/同一表格列，
严格归因判为未命中。该用例已因 `task_completion` 失败，此项不改变结论。

### A.6 仍未解决的问题

1. Prompt .2 未能阻止“完整维度查询后再 `top_n`”的冗余调用（008/015/026）。
2. 单例预算与重试策略不匹配：一次逻辑调用最多约 60 s，120 s 预算只能容纳约两次。
3. 剩余时间守卫的 5 s 阈值低于一次调用的最坏耗时，仍会发起注定失败的调用。
4. 部分结论的句式会让严格数字归因漏判（026 的 `number_accuracy=false`）。
5. 029、034、040 及全部安全/缺数用例在本轮仍未执行，Phase 7.3 的相关修复未获真实模型验证。
6. 20 条中 13 条未执行，本轮不构成 `first-round-20` 的完整结果。

### 16.1 `number_accuracy` 的正向结果

答案是 Markdown 表格（表头“库存天数（天）”），Phase 7.5 的表格列归属逻辑给出了 `true`；`numeric_validation_passed` 也为 true。**这是真实模型输出上的首次通过**，与 A 批“正确数字被分号切断而误判”的情形不同。

边界说明：本次输出是表格形态，未覆盖 A 批原文那种“分号 + 首条值”句式。因此这证明“表格列归属可用”，但不单独证明分号句式在真实模型下已修复（那部分只有离线用例证据）。

### 16.2 `conclusion_overreach` 是假阳性（新发现的评分器缺陷）

- 评分器警告：`模型结论包含无法在工具证据中直接核对数字：26.762447, 26.642075, 87.345507, 79.203518, 30.000000`。
- 事实：这 5 个值全部是 `query_metric` 返回的真实值，且模型已在工具消息中看到（见第 13 节）。
- 根因（代码定位）：`graph.py:1844 _unverified_numbers()` 只在 `evidence.result_summary` + `verified_findings` + ID 中查找数字；`evidence.result_summary` 是摘要，仅含“首条值 26.713990、末条值 0.000000”。多行明细虽已进入模型上下文，却没有进入评分器的核对语料。
- 性质：这是与 A 批同类的**信息不对称**，但发生在评测器一侧，不是模型编造数字，也不是 Phase 7.5 的可见性修复失效。
- 影响：任何“按行汇报多行结果”的用例都可能被误判失败，B 批多工具/多行场景风险更高。
- 本次**未修改**评分器、未修改预期答案、未调整容差，以保持测量有效。

### 16.3 评分器漏掉的真实错误（假阴性）

模型在“已验证发现”中写道：“P008 分母（14779.000000）为 8 个产品中最大”。离线核对：分母最大的是 **P003（18,163）**，P008 为 14,779。这是事实错误的比较结论，但 `unsupported_claim=false`、`safety_intercepted=null`，评分器**未捕获**。

结论：本例同时暴露评分器两个方向的偏差——把有据数字判为无据，又把无据比较判为可接受。`passed=false` 不能直接解读为“模型答错”，`number_accuracy=true` 也不能直接解读为“所有结论都正确”。

## 20. 是否建议进入第三轮 B 批

**暂不建议直接进入 B 批。**

理由：本次复测已证明 Phase 7.5 的核心目标（模型能看到并使用完整明细）在 026 上成立；继续阻塞 B 批的不是 Agent 可见性，而是**评分器两侧偏差**：`conclusion_overreach` 会把真实多行数字判为无据，B 批多工具/多行用例会大量复现；同时错误比较未被捕获，会高估模型正确性。

建议的下一步（需新的明确授权，且仍限定离线优先）：
1. 修复 `_unverified_numbers()` / `_evidence_number_values()` 的核对语料，使其包含工具结果中的明细值（含去重复用回传的可见数据），并加离线正/反用例：真实多行值通过、编造值仍失败、错误比较仍失败。
2. 将实际发送给模型的工具消息（或可见 `data` 的哈希与行数）写入评测归档，消除“只能推断”的可观测性缺口。
3. 上述修复完成并离线回归后，先重跑 026 一次确认判定稳定，再决定 B 批。

本阶段到此停止：未启动 B 批、C 批或完整 92 例，未自动重跑，未修改 Prompt、预期答案、canonical 值或容差，未覆盖任何历史归档。

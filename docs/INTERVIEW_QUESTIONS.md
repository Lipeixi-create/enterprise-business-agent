# Agent 应用开发岗位 — 高频面试题（基于本项目）

> 生成日期：2026-11-10。所有答案都对应本仓库的真实实现与已验证数据；未验证的部分会明确标注。
>
> **使用方法**
> 1. 第一遍通读「回答」，对照代码确认细节；
> 2. 第二遍只看问题做自测，能讲出 3 个要点即算通过；
> 3. 第三遍按 STAR 把项目讲成故事，重点准备第 0 节和第 12 节。
>
> **红线**：不说“生产级/高可用”，不说“多 Agent”，不说“用了 RAG”，不报没跑过的数字，不把脚本化测试说成真实模型结果。

## 0. 开场：项目陈述

### Q0-1. 用 1 分钟介绍这个项目

**回答模板**

> 这是一个企业多部门经营分析 Agent。用户用中文问“为什么本季度利润下降”，Agent 会自主决定下一步查什么，跨销售、营销、财务、供应链、人力五个域调用只读工具，最后输出每个数字都能追溯到证据的归因报告和结构化报告。
>
> 核心技术选择是：**语义层定口径、确定性引擎算数、证据账本做追溯，LLM 只决定“下一步做什么”**。因为 Text-to-SQL 的三个问题是口径不一致、数字不可信、权限不可控。
>
> 技术栈是 FastAPI + LangGraph + PostgreSQL 16 + OpenTelemetry。验证上，离线回归 765 个测试，真实 GLM 跑了 92 题，真实 PostgreSQL 做了 30 项验收，Docker Compose、外部 OTLP 和浏览器端到端都实跑过。

**加分**：最后补一句边界——“托管 PostgreSQL、多节点、TLS 这些生产项没有验证，我不会把它说成生产就绪。”

### Q0-2. 用 3 分钟讲清楚“一次请求发生了什么”

按这条链路讲，每一跳都能落到代码：

```
POST /agent/runs/async
→ 鉴权 + 幂等键创建 Run（queued）
→ 后台 Worker 抢占（条件 UPDATE + claim_version）
→ LangGraph decide：检查取消/截止时间/Token 预算 → 调 LLM（带 8 个工具）
→ 模型返回 tool_call → act：语义去重 → 重新授权 → 工具执行
→ 工具内部：Metric Resolver → Query Compiler → Semantic Guard → 只读执行
→ 生成 Evidence（落库、ID 回填）→ tool message 回灌
→ 回到 decide，直到模型不再调用工具
→ 最终答案：数字校验 + 关系校验 + 有界纠错
→ Phase5 Pipeline：Evidence → Finding → 归因 → 12 区块报告 → Numeric Validator
→ 人工审批（版本 + 指纹绑定）
```

**追问预警**：“中间任何一步失败会怎样？”——答：每种失败都有显式终态和 `stop_reason`，不用“成功”掩盖未完成。

### Q0-3. 这个项目最难的部分是什么？

> 不是接 LLM，而是**让 LLM 的自主性不破坏数据可信性**。工具选择要自由，数字和权限必须确定。
>
> 三个具体难点：
> 1. **语义去重**——既不能重复查询浪费预算，也不能误杀合法的新请求；
> 2. **数字校验**——既不能放过编造，也不能误杀合法的派生计算；
> 3. **预算调度**——既不能过早放弃，也不能发起注定超时的调用。

## 1. Agent 架构与编排

### Q1-1. 为什么用单 Agent 而不是多 Agent？

**考察点**：是否理解多 Agent 的成本，而不是跟风。

**回答**

- 五个业务域是**工具维度**，不是 Agent 维度。一个工具注册表加条件边就能表达“先查财务、再查销售”；
- 多 Agent 会引入路由、上下文同步、冲突合并和调试成本，收益在这个场景不明确；
- 单图的可观测性更好：一次 run 的 span 树是完整的，失败可以逐节点归因；
- 状态只有一份，checkpoint 和恢复简单。

**追问：什么情况会上多 Agent？**

- 子任务需要不同工具集、不同上下文窗口、不同权限边界，且可以并行；
- 需要独立的评审/对抗角色（critic、verifier）；
- 单个上下文装不下全部工具描述（几十个以上工具时，需要路由层先缩小工具集）。

**加分**：说清楚“我现在的工具只有 8 个，单 Agent 完全够；如果工具涨到 50 个，我会先做工具检索/分层，而不是直接上多 Agent。”

### Q1-2. LangGraph 的状态是怎么设计的？

**回答**

- `AgentGraphState` 是 `TypedDict`，只放**可序列化**的东西：问题、消息、步骤、观察、证据、预算计数、错误、`pending_action`、`stop_reason`；
- 不可序列化的东西——`cancel_event`、单调时钟 `deadline`、trace sink、span sink——放在进程内 `_RunContext`，按 `run_id` 索引；
- 这是让状态能安全 checkpoint 的关键：取消事件和上一个进程的 deadline 本来就没有序列化意义；
- 图只有两个节点：`decide` 和 `act`，条件边是 `pending_action` 存在则去 `act`，否则 `END`。

**加分**：`recursion_limit=50` 作为兜底，真正的停止靠预算和终止条件，不靠递归上限。

### Q1-3. `decide` 节点具体做什么？

按顺序：

1. 取消检查（`cancel_event.is_set()`）；
2. 终态检查（已失败/超时/预算耗尽就不再决策）；
3. 硬截止时间检查；
4. **剩余时间是否够一次模型调用**：`required = max(5s, min(llm_timeout, 上次调用耗时))`，不够就停；
5. Token 预算检查；
6. 按当前 principal 取可用工具（预算为 0 时给空列表）；
7. 构造提示词，调用 `complete_with_tools`；
8. 解析：有 `tool_calls` → 写 `pending_action`；没有 → 进入最终答案处理。

**陷阱**：不要说“每轮都调用模型直到预算用完”。模型给出最终答案就结束，预算只是上限。

### Q1-4. `act` 节点具体做什么？

1. 语义去重：已有结果能否覆盖这次调用；
2. 命中则用**当前 principal** 重新授权（防角色降级穿透）；
3. 查工具结果缓存（用于续跑重放），重放同样要重新授权；
4. 执行：超时 + 有限重试；
5. 证据落库，把 run 级 evidence_id 回填到模型可见的 draft；
6. 生成 tool message 回灌，更新计数、错误、覆盖记录；
7. 权限拒绝 → 直接终止（不允许模型换说法绕过）；
8. 连续失败达到阈值 → `tool_failure`。

### Q1-5. Agent 的终止状态有哪些？为什么这么多？

`completed`、`completed_with_warnings`、`no_evidence`、`no_data`、`budget_exhausted`、`timeout`、`llm_unavailable`、`llm_timeout`、`invalid_action`、`repeated_tool_call`、`tool_failure`、`cancelled`、`failed`。

**回答要点**：状态即契约。调用方、告警、评测都需要区分“成功”“有警告的成功”“没证据”“模型不可用”“预算耗尽”。如果只有一个 `success/fail`，评测和排障都会失真。

### Q1-6. 模型说要调用工具，但参数是错的，怎么办？

分三类：

- **参数不符合 schema**（`invalid_arguments`）：把校验错误回灌给模型，让它自己改，不消耗终止额度；
- **动作非法**（`invalid_action`，比如不存在的工具）：有界重试（默认 1 次），超限终止；
- **完全相同的调用**：用 `sha256(canonical json)` 检测重复，直接终止（`repeated_tool_call`）。

### Q1-7. 模型一轮返回多个工具调用怎么办？

只执行第一个，其余忽略并写 warning。理由：

- 单步执行才能保证“观察 → 决策”的因果链；
- 并行执行会让证据顺序、预算计数、失败语义变复杂；
- 真实场景里模型一轮多调用通常说明它没在认真看上一轮结果。

### Q1-8. 什么是“语义去重”？为什么不直接用参数哈希？

**回答**

- 参数哈希只能挡住完全相同的调用；
- 语义去重判断的是**已有结果能否覆盖新请求**：指标、时间范围、过滤、维度、粒度/聚合、排序方向、结果完整性；
- 例子：已经查过 `query_metric` 某维度的全部成员，模型再调同维度的 `top_n`，可以直接复用；
- 反过来，`query_metric` 的可见视图被截断时，不能拿去回答 `top_n`，因为数据不全。

**追问：复用会不会绕过权限？**

不会。复用前用**当前 principal** 对原始参数重新授权；角色降级后，去重路径同样被拒。

### Q1-9. 工具结果缓存和去重有什么区别？

| | 缓存 | 语义去重 |
| --- | --- | --- |
| 范围 | 同一 run，工具结果持久化 | 同一 run，已成功结果的覆盖关系 |
| 用途 | 进程重启后续跑重放 | 运行时避免重复查询 |
| 命中后 | 重放结果，仍重新授权 | 返回已有证据，不消耗工具预算 |
| 不缓存的 | 权限拒绝、非法动作（必须重新判定） | — |

### Q1-10. Agent 怎么知道“调查够了”？

- 模型自己给出最终答案（主要机制）；
- 证据已覆盖：提示词要求“证据足够时立即结束，不要为完整性重复查询”；
- 预算兜底：工具数、时间、Token；
- 无新信息：语义去重挡住重复查询，模型拿不到新数据，自然会收敛。

**加分**：说一句“Agent 的收敛靠提示词 + 去重 + 预算三重作用，不靠单一阈值。”

## 2. 工具调用 / Function Calling

### Q2-1. 工具是怎么注册的？

`ToolDefinition`：名称、描述、Pydantic 参数模型、handler、所需 scope、超时、是否访问数据。

`spec()` 把 Pydantic 模型转成 JSON Schema 给模型。8 个工具：

`list_metrics`、`describe_metric`、`query_metric`、`compare_periods`、`top_n`、`contribution`、`trend`、`anomaly_scan`。

### Q2-2. 工具设计有哪些原则？

- **单一职责**：查数、对比、排名、贡献、趋势、异常分开，模型更容易选对；
- **只读**：没有任何写工具；
- **结构化返回**：状态、摘要、数据、错误码、证据 ID 分开；
- **自带证据**：每次成功调用都产生 EvidenceDraft；
- **幂等**：同样的参数同样的结果，可以安全重放；
- **可分类的错误**：`permission_denied` / `invalid_arguments` / `timeout` / `invalid_action` 分别处理；
- **模型可见数据有截断**：给摘要 + `row_count/displayed_count/truncated`，而不是把 200 行全塞进上下文。

### Q2-3. 为什么不让模型看全部数据？

- 上下文成本和注意力稀释；
- 让模型基于**工具已算好的结果**做判断，而不是自己逐行算；
- 截断标记会进入去重逻辑，防止用不完整的视图回答新问题；
- 需要汇总时，让模型调用 `top_n` / `contribution`，而不是自己累加。

### Q2-4. 怎么让模型选对工具？

- 工具描述写清楚“什么时候用”：排名用 `top_n`、趋势用 `trend`、异常用 `anomaly_scan`；
- 系统提示里给出明确的工具选择规则（本项目 25 条规则）；
- 参数 schema 注入动态 enum：指标、维度直接枚举，减少幻觉；
- 工具错误回灌时带 `recovery_hint`；
- 评测里单独评“工具选择”和“工具参数”两个维度。

**陷阱**：不要把所有逻辑塞进一个万能工具，模型会选错参数。也不要把工具拆得太细，模型会组合不动。

### Q2-5. Function Calling 和 ReAct / 手写 JSON 解析有什么区别？

- Function Calling 是 provider 原生能力，工具调用有结构化的 `tool_calls` 字段，不需要正则解析；
- ReAct 是提示词范式（Thought/Action/Observation），可以套在 Function Calling 上；
- 手写 JSON 解析脆弱，容易在半截 JSON、markdown 代码块上翻车；
- 本项目用原生 Function Calling，但**空响应**和**非法动作**仍有有界重试，因为 provider 偶尔会返回空。

### Q2-6. 工具超时怎么处理？

- 单工具超时 = `min(agent_tool_timeout, 剩余时间 / 尝试次数)`；
- 超时算失败，计入连续失败；达到上限终止；
- 已知局限：超时依赖线程 Future，超时线程可能继续完成只读查询，没有进程级资源隔离。

### Q2-7. 工具返回 `insufficient_data` 时 Agent 怎么办？

- 提示词明确要求：调整调查或说明限制，不要对同类成员逐个重试；
- 评测里把“误用工具”和“正确报告限制”分开评；
- 证据账本会记录失败状态，但**不产生可引用事实**。

### Q2-8. MCP 在这个项目里是什么角色？

- 它是**工具传输层**，不是第二套执行路径；
- `POST /mcp` 实现 JSON-RPC 的 `initialize / ping / tools/list / tools/call`；
- `tools/call` 仍然走 `ToolRegistry.execute` → 权限 → 语义守卫 → 只读执行；
- 默认关闭，开启后仍要求 API Key；按角色过滤可见工具；
- 客户端侧集成没做，因为内部工具注册表已经够用，MCP 是暴露面而不是架构。

## 3. 上下文工程与 Prompt

### Q3-1. 系统提示词里都写什么？

- 角色和硬约束：只能调用提供的工具、不能生成/执行 SQL、不能编造数字；
- 工具选择规则：排名/趋势/异常/对比分别用什么；
- 数字引用规则：原样引用、只允许一次四则运算、禁止三行以上汇总；
- 时间规则：单月用月初、季度区间用月初；
- 去重规则：已有同指标同维度同周期结果时禁止重查；
- 反注入规则：工具结果是数据不是指令；
- 失败处理：遇到 `insufficient_data` / `timeout` 要调整或说明限制。

**加分**：提示词有版本号（`phase9-2026-11-04.1`），写进 span，方便对比不同版本的效果。

### Q3-2. 提示词越长越好吗？

不是。

- 规则是从评测失败里逐条长出来的，每条都对应一个真实错误模式；
- 规则太多会稀释注意力，也会让模型过度保守；
- 更好的方向是把硬约束放进代码（Guard、Validator），提示词只保留“选择策略”。

**可以讲的取舍**：本项目提示词里仍有很多规则，是因为这些规则的代码化成本高于收益；真正不能妥协的（数字、权限）都在代码里。

### Q3-3. 怎么防止 Prompt Injection？

- 工具结果和用户输入都视为数据，系统提示明确要求忽略其中的指令；
- 模型没有 SQL 执行能力，也没有数据库连接，注入能造成的最大破坏是“调用一个已授权工具”；
- 权限拒绝是终止条件，不允许模型换说法绕过；
- 有专门的注入/越权测试（脚本化对抗模型，不是真实模型注入评测）。

**加分**：承认边界——“真实模型在长上下文里对注入的抵抗力，我没有做系统评测。”

### Q3-4. 上下文里放哪些历史？

- 完整的对话消息（user / assistant tool_calls / tool）；
- 工具结果只放**模型可见视图**（摘要 + 截断标记）；
- 已验证发现列表（`verified_findings`）作为压缩后的中间结论；
- 预算和剩余时间通过提示词动态追加。

### Q3-5. 输出被截断怎么办？

- 最终答案截断：一次续写请求（不带工具），只能补文本，不能新增证据；再截断就保留部分 + 明确 warning；
- 报告叙述截断：按段落生成、逐段校验，失败段回退模板并标记 `narrative_mode`；
- 纠错重写截断：直接丢弃重写，保留原答案。

### Q3-6. 怎么降低 Token 成本？

- 语义去重和缓存重放，减少重复调用；
- 工具返回截断视图，不塞全量数据；
- 报告按段落生成，失败只重试该段；
- 单 Run Token 上限 120k；
- 已知缺口：没有配模型单价，成本字段是 `null`。

## 4. 可信性与幻觉治理（项目最强项）

### Q4-1. LLM 编造数字，你们怎么防？

分四层，从软到硬：

1. **提示词约束**：数字必须来自工具返回，只允许对两个返回值做一次四则运算；
2. **代码硬校验**：收集工具返回的所有数字，生成派生候选（两两加减乘除、必要时三/四数求和），最终答案里的数字必须命中其中之一；
3. **有界纠错**：命中失败时让模型重写一次（不给工具），只有违规数减少才采纳；
4. **报告层校验**：Numeric Validator 校验引用、单位、时间范围、筛选口径、因果表述。

**追问：怎么处理百分比和舍入？**

校验器允许“原值 × 100”和 0–6 位小数的等价形式，但**只接受量化后的精确匹配**，不接受容差带内的“近似数字”。

### Q4-2. 为什么不直接让模型别编？

因为提示词是概率约束，不是保证。

- 模型会在长上下文里忘记规则；
- 模型会自己“心算”三行汇总；
- 模型会把百分比和绝对值混用。

代码校验是确定性的，提示词只是第一道防线。

### Q4-3. 数字校验会不会误杀合法数字？

会，所以设计了三层放宽：

- 百分比等价（`0.246663` ↔ `24.6663%`）；
- 0–6 位小数舍入等价；
- 两个原值的一次四则运算。

仍不接受“看起来差不多”的模糊匹配，避免把巧合数字当真。

**加分**：说清楚“误杀会降低体验，放过会破坏可信性，我选择偏向可信，并用有界纠错来降低误杀的体感成本。”

### Q4-4. Evidence（证据）包含哪些字段？

`run_id`、`tool_call_id`、指标与口径版本、时间范围、粒度、筛选、维度、查询参数、原始结果、单位、来源表、计算方法、`query_hash`、状态、置信度。

设计原则：**任何一条结论都能顺着 evidence_id 追到 tool_call_id，再追到具体的查询和计算。**

### Q4-5. 证据怎么去重？

按 `(run_id, fingerprint)` 去重。指纹包含指标、时间范围、筛选、粒度、维度。

- 同一 run 内相同查询不重复入库；
- 不同时间范围或不同筛选**不合并**，因为它们是不同事实。

### Q4-6. Finding 是怎么生成的？为什么不让 LLM 写？

- 规则引擎从 Evidence 生成：事实、变化、异常、贡献、相关、假设、建议；
- 每条 Finding 必须引用 evidence_id，置信度由规则计算；
- 相关性用“可能相关 / 需要进一步验证”，**不写因果**；
- LLM 只负责自然语言叙述，不负责结论结构。

### Q4-7. 归因和因果的区别？

- 归因是**统计分解**：`Δ_i / Δ_total`，回答“变化里各部分占多少”；
- 因果需要反事实或实验，同期相关性不能证明因果；
- 报告里明确写“统计贡献不等于因果”，这是产品约束，不是文字游戏。

### Q4-8. 报告结构是怎么保证的？

- 12 个固定区块，由代码生成骨架；
- 结论引用 `finding_id`，业务数字用 `ValueReference` 指向 evidence 原值；
- 报告按 `(run_id, report_version)` 追加版本，不覆盖历史；
- LLM 叙述逐段生成、逐段校验，失败回退确定性模板。

### Q4-9. 校验失败怎么办？

- 保留结构化错误和修正记录；
- 有限次修正后回退确定性报告；
- **不关闭规则**换通过率，这是红线。

### Q4-10. 怎么处理“业务关系错误”？

除了数字，还有关系校验：最高/最低是否唯一、排名顺序、变化方向、单位是否一致。

- 例如模型说“A 最高”，但数据里 B 更高；
- 发现关系问题后同样走一次有界纠错；
- 评测里把这类错误单独归类，避免和“数字错误”混在一起。

## 5. 评测（Agent 岗位必问）

### Q5-1. 你们的 Agent 怎么评测？

- **语料**：92 条业务问题，覆盖五个业务域、跨域、异常归因、指标歧义、缺数、零分母、越权、注入、预测、多步调查；
- **真值**：由同一确定性数据库上的 canonical 查询生成，构建脚本强制人工复核，不手写期望数字；
- **多维评分**：工具选择、工具参数、查询结果、任务完成、Evidence 引用完整度、Finding 引用正确率、Numeric Validator、报告结构、数字准确、安全拦截、错误拒绝、叙述完整；
- **门禁**：普通 `pytest` 默认排除 `live_model`，真实模型必须显式 `--allow-live-model`；
- **分栏记录**：真实模型 / 脚本化假客户端 / 未执行，严格分开。

### Q5-2. 为什么不用 LLM-as-judge？

- 业务问题的对错是**可判定**的：数字对不对、有没有引用证据、工具选得对不对；
- LLM judge 会引入新的不稳定性和偏差，且难以解释失败原因；
- 现阶段用规则 + 确定性比对更可靠。LLM judge 可以作为补充，不能作为唯一标准。

### Q5-3. 真实模型的评测结果是多少？

诚实回答：

- 92 条执行、90 条计分、210 次真实调用，as-run **69/90**；
- 用修复后的评测器离线后验是 **76/90**，但这是离线复算，**不是新的真实运行**；
- 失败拆分：5 个 provider 不可用 + 7 个评测器误报 + 9 个保留契约偏差；
- 多种子 24 条 × seeds 42/7/123：通过率 54.55% / 63.64% / 72.73%。

**陷阱**：不要把 76/90 说成真实通过率，也不要把不同 seed 的结果混算。

### Q5-4. 评测器本身错了怎么办？

- 逐条归因，识别出 10 类解析/归属错误（变化字段提示、括号遮蔽、比较短语、排名区间、排名列示主语、排序线索门禁、指标边距距离、子集作用域、全负贡献方向等）；
- **修评测器，不改 Ground Truth、不改 required_calls、不改阈值**；
- 新增 8 个负向回归测试 + 3 个正向对照，确认守卫没有屏蔽真实错误；
- 这是我认为最能体现工程判断的一段：调评测器比调模型更容易自欺。

### Q5-5. 怎么评测可靠性而不是质量？

- 超时、取消、预算耗尽、数据库故障、模型故障、重启中断都有专门测试；
- 断言的是**终态和副作用**：不伪造成功、不产生工具调用、不残留证据、不重复 `run_finished`；
- 真实 PostgreSQL 专项 30 项，覆盖权限、并发、租约、幂等、隔离。

### Q5-6. 怎么防止评测集过拟合？

- 语料按业务域和题型分层，不按模型错误定制；
- 真值来自 canonical 查询，不来自模型输出；
- 失败归因时区分“能力问题”和“评测器问题”，只有前者才考虑改系统；
- 有独立的安全和越权用例，不能靠调提示词通过。

### Q5-7. 线上怎么评估？

现在的评测是离线 + 真实模型批量。线上可以补：

- 运行质量指标（成功率、P95 延迟、工具错误率、审批积压）；
- 人工审批作为弱标签（通过/驳回率）；
- 失败样本回流到评测集。

**坦白**：线上 A/B 和灰度没做。

### Q5-8. 为什么有些用例不通过？

三类：

- provider 不可用（网络/服务端问题）；
- 保留的契约偏差（比如拒绝越权但没有调用 `query_metric` 触发规范错误码）；
- 模型对回答边界的理解不稳定（同一问题两次结果不同）。

### Q5-9. 评测指标怎么设计才不刷分？

- 多个维度分开算，不合成一个总分；
- 安全拦截和错误拒绝单独算，避免“答得多”掩盖“答错”；
- 数字准确率和任务完成率分开，避免用华丽叙述掩盖错误数字；
- 记录失败原因分布，而不只记录通过率。

### Q5-10. 一次评测跑多久？成本多少？

- 92 题真实模型约 210 次调用，P50 32.5s / P95 102.1s；
- 离线回归 765 个测试约 90 秒；
- 成本字段是 `null`，因为没配单价。

## 6. 可靠性与生产化

### Q6-1. LLM 调用超时怎么设计？

- **三类超时分离**：连接、读取、单请求总墙钟；
- 总墙钟防止 provider 用慢速字节流绕过读取超时；
- Run 级别的硬截止时间通过 `ContextVar` 传播到所有模型调用；
- 每次 HTTP 交换在独立线程执行，调用线程每 ≤50ms 轮询取消和总超时；
- 超时/取消时 `shutdown` 底层 socket 唤醒阻塞读，`close()` 放到守护线程。

**追问：为什么要放守护线程？**

httpcore 在 TLS 握手卡住时持有连接锁，`close()` 会一直等，导致调用线程被阻塞、总超时无法抛出。这是容器里一次 32 分钟停顿暴露出来的。

### Q6-2. 超时之后会重试吗？

分情况：

- 普通 provider 超时 → `llm_timeout`，允许有限重试；
- Run 硬截止时间到 → `timeout`，**不重试**，因为重试注定失败；
- 剩余预算不足以完成“退避 + 最小请求窗口（5s）” → 不重试。

### Q6-3. 重试策略是什么？

- 故障分类：timeout / connection / rate_limit / server / auth / protocol / circuit_open；
- `401/403` 不重试；
- `429/5xx/timeout/connection` 指数退避：`min(0.5 × 2^attempt, 8s)`；
- `Retry-After` 解析后截断到上限（默认 30s）；
- 连续失败 3 次熔断，冷却 30s 后半开，只允许一个探测请求。

### Q6-4. 熔断器为什么按客户端实例而不是全局？

- 当前是单实例部署，按实例计数足够；
- 全局熔断需要共享状态（Redis），会引入新的故障点；
- 已知局限：多实例下每个实例独立熔断，可能放大上游压力。如果要上多实例，应该换成共享计数 + 抖动。

### Q6-5. 怎么保证同一个请求不被重复执行？

- 幂等键：客户端提交时带幂等键，相同键只创建一个 Run；
- 数据库唯一约束兜底；
- 并发测试：4 线程同幂等键只生成 1 个 Run。

### Q6-6. 多 Worker 怎么避免同时跑同一个 Run？

- **抢占**：条件 `UPDATE ... WHERE status='queued' AND claim_version=?`；
- **租约**：Worker 定期续期，过期后其他 Worker 可以接管；
- **Fencing**：每次接管 `claim_version + 1`，旧 Worker 的写入因为版本不匹配被拒绝；
- 冲突返回 409；
- 测试覆盖两个独立进程并发抢占、租约过期接管。

### Q6-7. 进程重启后未完成的 Run 怎么办？

- 启动时把非终态 Run 标记为 `interrupted` / `process_restart`；
- LangGraph checkpoint 保留状态，可以显式 resume；
- 工具结果缓存重放，避免重复执行；
- 恢复时会用当前 principal 重新授权，角色变化立即生效。

### Q6-8. 取消是怎么实现的？

- 协作式取消：`cancel_event` 在每个决策点检查；
- 模型调用阻塞时，通过 socket shutdown 中断；
- **取消优先于持久化**：已到达的取消不会被完整回答覆盖；
- 工作台在取消后有界轮询终态（最多 30s），避免 UI 停在 `cancelling`。

**加分**：这是浏览器 E2E 发现的真实 bug——服务端已经 `cancelled`，UI 还停在 `cancelling`，因为取消后只刷新了一次。

### Q6-9. 怎么限制单个 Run 的成本？

- 工具调用上限 6；
- 单 Run 墙钟上限 300s；
- Token 上限 120k；
- 单次模型输出上限；
- 剩余时间不够一次调用就提前停止。

### Q6-10. 已知的可靠性缺口是什么？

- 工具超时依赖线程 Future，没有进程级资源隔离；
- 熔断是进程内；
- 多进程“阻塞请求 + 租约接管”组合没实测；
- 超时清理阻塞的修复没有在真实网络停顿中复验；
- 容器到 provider 的网络时通时断，不能宣称稳定。

## 7. 安全与权限

### Q7-1. 怎么防止 SQL 注入？

模型根本不接触 SQL。

链路是：结构化参数 → Query Compiler（白名单标识符 + 绑定参数）→ Semantic Guard（只接受编译后的结构化查询）→ SQLGlot AST Guard → 只读执行器。

任意一层拒绝都不会执行。AST Guard 还会拒绝注释、字面量过滤值、多语句、DDL/DML、未知表和函数。

### Q7-2. 为什么是“结构化查询契约”而不是“校验 SQL 文本”？

- 事后解析 SQL 文本总有绕过空间（等价改写、函数嵌套、方言差异）；
- 结构化契约在**生成阶段**就限制了可能的空间；
- AST Guard 是第二道防线，不是唯一防线。

### Q7-3. 权限模型是什么？

- API Key 认证，`X-API-Key`，`hmac.compare_digest` 常量时间比较；
- 角色 scope：`metrics:read`、`agent:run`、`approval:decide`、`resource:read_any`；
- 数据策略：角色级指标/维度/区域限制；
- 区域受限角色必须显式过滤区域，不能省略过滤读全国汇总，也不能只按区域分组绕过；
- run / evidence / finding / report / approval 按 principal 隔离。

**坦白**：这不是完整 RBAC/RLS，没有列级权限。

### Q7-4. 角色被降级后，缓存和去重会不会泄漏数据？

不会，两处都做了重新授权：

- 工具结果重放前，用当前 principal 对原参数重新授权；
- 语义去重复用前，同样重新授权。

这是我认为容易被忽略、但真实存在的漏洞面。

### Q7-5. 怎么防止越权访问别的用户的运行？

- 所有资源查询都带 principal 过滤；
- 跨账号访问返回 404，不返回 403（避免泄露资源是否存在）；
- admin 角色（`resource:read_any`）可以读全部；
- 有专门测试覆盖 Evidence / Finding / Report / Approval 的跨账号隔离。

### Q7-6. 日志里会不会泄露密钥？

- 密钥字段 `repr=False, exclude=True`；
- JSON 日志对 API Key、密码、连接串、Authorization 递归脱敏；
- 审计只记录 SQL 哈希、表名、行数、耗时、状态，不记录 SQL 原文和参数值；
- Prompt 和响应内容不写日志，只记录模型、耗时、Token 数。

### Q7-7. 越权请求一定要模型“自觉”拒绝吗？

不。

提示词要求模型对越权指标仍发起一次受控查询，让权限层给出权威拒绝。按钮不在模型手里，在代码里。

### Q7-8. Prompt Injection 能造成什么实际危害？

在这个架构下，最坏情况是模型调用一个**已授权**的工具，然后把结果组织成误导性叙述。它不能：

- 执行 SQL 或写数据库；
- 越权读数据；
- 改系统规则；
- 获得数据库凭据。

数字和关系错误还有二次校验兜底。

## 8. 可观测性与运维

### Q8-1. 一次 Run 的 trace 长什么样？

```
http.request
└── agent.run
    ├── agent.decision
    │   └── llm.complete
    ├── tool.call
    │   └── db.query
    ├── evidence.collect
    ├── finding.build
    ├── report.generate
    └── approval.ensure
```

### Q8-2. 异步 Run 怎么延续 trace？

请求线程创建 trace context，后台 Worker 通过显式 context 继承，而不是依赖线程本地变量。否则异步执行的 span 会变成新的 trace 根。

### Q8-3. 导出方式有哪些？

`file`（JSONL）、`otlp`（OTLP/HTTP）、`console`、`none`。

- 只有导出真正返回 `SUCCESS` 才计入 `exported_spans`；
- 本地用 file 排障；生产指向 Collector；
- 已验证自建 Collector 收到 257 个 span；托管后端没验证。

### Q8-4. 告警怎么做的？

`GET /api/v1/alerts`（仅 admin），评估：

- 失败率；
- P95 延迟；
- 审批积压；
- LLM 超时；
- 数据库连接错误；
- tracing 开启但未初始化。

只有轮询接口，不发送外部通知。

### Q8-5. 线上出问题怎么定位？

按这个顺序：

1. `/health` 看数据库和 LLM 配置；
2. `/api/v1/metrics` 看成功率、延迟、工具错误率；
3. trace 看是哪一跳慢/失败；
4. run 详情看 `stop_reason` 和 `errors`；
5. 证据账本看数据是否真的缺失。

### Q8-6. 怎么衡量 Agent 的质量？

- 业务指标：任务完成率、数字准确率、证据引用完整度；
- 工程指标：成功率、P95 延迟、工具错误率、平均迭代数、Token 成本；
- 人工信号：审批通过/驳回率。

## 9. 数据、语义层与 SQL

### Q9-1. 为什么要有语义层？

- 统一口径：“利润”是毛利还是净利，“ROI”分子分母怎么定义；
- 可测试、可版本化、可审计；
- 大多数经营问题可以表达成“指标 + 维度 + 时间 + 对比”，不需要自由 SQL；
- 自由 SQL 只作为兜底，且必须过 Guard。

### Q9-2. 指标定义包含什么？

label、同义词、业务域、口径说明、来源表/字段、分子/分母、聚合方式、可加性、单位、可用维度、时间粒度、空值和零分母行为。

### Q9-3. 加性 / 半加性 / 比率的区别？

- 加性：销售额、成本，跨时间求和；
- 半加性：库存、人数，取期末值，不能跨时间求和；
- 比率：毛利率、ROI、缺货率，分别汇总分子和分母再相除。

比率直接平均是常见错误，必须按分子/分母汇总。

### Q9-4. 零分母和缺数怎么处理？

- 分母为 0 → `not_calculable`；
- 时间范围不完整或基准缺失 → `insufficient_data`，返回 `missing_periods`；
- 真实 0 和“算不出来”永远是两种状态。

### Q9-5. 为什么不用 Text-to-SQL 直接查？

- 口径不可控；
- 生成的 SQL 难以审计；
- 权限边界难保证；
- 数字来源不可追溯。

语义优先 + 受限 SQL 兜底的组合，在可控性和覆盖率之间更平衡。

### Q9-6. 指标歧义怎么处理？

返回 `ambiguous` 和候选，不静默选择。例如“利润率”候选 `gross_margin` / `net_margin`，“利润”候选 `gross_profit` / `net_profit`。调用方必须改用 canonical 名称或补充口径。

## 10. 横向：RAG、记忆、多 Agent、协议（2026 岗位常见）

### Q10-1. 你这个项目为什么不用 RAG？

- 经营问题需要精确聚合和可复现数字，不是文本相似度；
- 数据在结构化数据库里，语义层已经能表达口径；
- RAG 适合非结构化知识：口径说明、业务规则、历史案例。

**加分**：如果要做，我会把“指标定义解释、历史分析案例、政策文档”做成知识工具，检索结果仍然要转成证据，不能让模型直接引用检索片段当数字。

### Q10-2. Agent 的记忆怎么设计？

分三层：

- **短期**：`AgentGraphState`，一次 Run 内的消息、观察、证据；
- **中期**：LangGraph checkpoint + 工具结果缓存，支持中断恢复；
- **长期**：目前没有用户偏好/历史结论的长期记忆；要做的话需要单独设计存储、更新和遗忘机制。

**坦白**：本项目没有做长期记忆，也没有做多轮对话上下文管理。

### Q10-3. 多 Agent 什么时候值得上？

- 子任务工具集差异大、上下文装不下；
- 需要并行调查（多个域同时查）；
- 需要独立评审角色；
- 需要不同权限边界。

代价：路由、状态同步、冲突合并、成本翻倍、调试困难。

### Q10-4. 怎么看 MCP 和 A2A？

- MCP 解决的是“Agent 怎么访问工具和数据源”，是工具层协议；
- A2A 解决的是“Agent 之间怎么协作”，是协作层协议；
- 两者不冲突。本项目只做了 MCP 服务端，因为内部工具注册表已经够用；
- 关键不是接协议，而是**协议后面有没有统一的权限和执行边界**。

### Q10-5. 模型升级/切换怎么保证不回归？

- Provider Factory，配置切换 provider / model / base URL；
- 提示词有版本号，写进 span；
- 换模型必须重跑评测语料，不能只看几个例子；
- 评测结果按模型和 seed 分栏记录。

### Q10-6. 如果要做多轮对话，你会怎么改？

- 引入 `conversation_id` 和会话级状态；
- 区分“对话上下文”和“Run 状态”：前者是消息历史，后者是调查状态；
- 证据跨轮复用要考虑时效和权限变化；
- 需要设计“指代消解”和“上下文压缩”。

### Q10-7. 如果工具涨到 50 个怎么办？

- 先做工具检索/分层：按业务域分组，先让模型选域再选工具；
- 工具描述标准化，避免语义重叠；
- 或者引入路由层（小模型分类），但要有评测证明路由准确率；
- 不是直接上多 Agent。

### Q10-8. 怎么控制 Agent 的延迟？

- 减少不必要的模型调用（去重、证据足够即停）；
- 工具查询下推数据库，不把全量数据拉回来算；
- 报告分段生成，失败只重试该段；
- 预算调度避免发起注定超时的调用；
- 坦白：单次真实任务 P95 超过 100 秒，延迟仍是弱点。

## 11. 压力追问（面试官常用）

### Q11-1. “你这个不就是个套壳 ChatGPT 吗？”

> 不是。ChatGPT 直接回答，我的系统回答不了的问题会明确说“数据不支持”，而且每个数字都能追到一条证据。模型在这里只做工具选择，数字和权限都是代码保证的。

### Q11-2. “你的准确率 69/90，不算高啊。”

> 对，而且我不会把它包装成更高。这 90 条里有 5 条是 provider 不可用，7 条是评测器误报，剩下 9 条是保留的契约偏差。我更在意的是**失败可归因**：每一条失败都能说清楚是模型、评测器还是系统边界的问题。多种子结果也说明模型本身有波动。

### Q11-3. “如果模型就是不按提示词来，你怎么办？”

> 提示词只是第一层。数字有代码校验，权限有 Guard，越权会终止，报告有 Numeric Validator。模型可以“不听话”，但它没有能力绕过这些层。

### Q11-4. “你这个系统能上生产吗？”

> 核心链路可以跑，但我不会说生产就绪。缺的是托管 PostgreSQL、多节点、TLS、备份/PITR、容量压测，还有密钥轮换的技术验证。已知的网络波动和 32 分钟停顿也说明容器到 provider 的链路不稳定。

### Q11-5. “为什么不用 Kafka / K8s / 微服务？”

> 当前规模不需要。单机 Compose 足够验证链路；引入消息队列和 K8s 会增加运维面，但不能解决核心问题（可信性和评测）。等有多实例和异步任务量需求时再引入。

### Q11-6. “你最大的技术判断失误是什么？”

> 初期把“模型可见数据”和“完整工具结果”混在一起，导致去重逻辑误判截断视图可以复用。后来把 `row_count / displayed_count / truncated / visible_complete` 显式建模，才修好。教训是：**给模型看的东西要当成正式契约设计。**

### Q11-7. “如果重做一次，你会先做什么？”

> 先做评测和 trace，再做 Agent。没有评测，改提示词就是盲调；没有 trace，失败只能猜。这个项目后期花了很多时间补评测器和归因，如果一开始就有，会省很多。

### Q11-8. “团队里有人要坚持用多 Agent / RAG，你怎么说服？”

> 不靠立场，靠评测。让他给出一个单 Agent 做不到的具体用例，然后用同一套语料对比通过率、延迟和成本。如果多 Agent 真能提升，我会支持；如果只是架构更酷，我会反对。

### Q11-9. “线上出了一个错误结论，你怎么排查？”

1. 看 run 的 `stop_reason` 和 `errors`；
2. 看 trace 哪一跳异常；
3. 看证据账本：证据是否缺失、是否被截断；
4. 看最终答案的数字校验结果；
5. 复现：用同一问题跑离线评测，确认是模型波动还是系统缺陷。

### Q11-10. “你怎么保证自己改的东西没把别的改坏？”

- 765 个离线测试；
- 真实 PostgreSQL 专项 30 项；
- 评测器有正向对照和负向回归；
- 改动提示词或校验规则必须重跑对应语料；
- 结果按真实/脚本/未执行分栏记录。

### Q11-11. “为什么用 GLM 不用 GPT/Claude？”

> 成本和可访问性是一方面，更重要的是 provider 抽象：我有统一 `LLMClient` 接口和 Provider Factory，换模型是配置问题。评测也证明了换模型必须重跑，不能假设通用。

### Q11-12. “你的系统里 LLM 到底做了什么？”

> 三件事：把自然语言规划成工具调用、在已有证据上决定下一步、写最终叙述。它不算数、不查库、不写库、不管权限。

## 12. 行为面与项目复盘

### Q12-1. 讲一个你发现并修复的真实 bug

**STAR**

- **S**：浏览器 E2E 跑取消流程时，服务端日志显示 0.8 秒内已经 `cancelled`，但 UI 停在 `cancelling` 两分钟；
- **T**：确认是服务端问题还是前端问题；
- **A**：查 SSE 和服务端日志，确认状态已落库；定位到 `cancelRun()` 中止进度流后只调用一次 `loadRun()`，如果服务端还在中间态就不再更新；改成取消后每 500ms 轮询，最多 30 次，直到终态；
- **R**：复测 UI 正确显示 `running → cancelling → cancelled`，并加了终态集合常量。

### Q12-2. 讲一个“看起来是模型问题，其实是系统问题”的案例

容器里一次模型调用 32 分钟才返回。表面看是 provider 慢，实际是：

- 配置 120s 超时没有生效；
- 调用线程卡在超时清理路径上；
- `client.close()` 被 httpcore 的连接锁阻塞。

修复：`shutdown` socket + 守护线程 `close()`。教训：**超时不是配一个数字，要验证清理路径本身不会阻塞。**

### Q12-3. 你怎么做技术取舍？

用“能不能验证”做标准：

- 能验证的优先（评测、测试、trace）；
- 不能验证但风险高的，明确标记未验证，不假装完成；
- 架构选择看收益/成本比，不看流行度。

### Q12-4. 你和“产品要求提高通过率”冲突过吗？

有过类似压力。我的底线是不改 Ground Truth、不改阈值、不改安全规则。可以通过修评测器误报、补提示词规则、改进工具来提升真实通过率；但不能把测试改成能过。

### Q12-5. 这个项目最大的收获？

> 可信性比智能性更难。让模型多说一句话很容易，让每个数字都能追溯、每个越权都被挡住、每个失败都能解释，才是工程。

## 15. 不要说的话

- ❌ “生产级 / 高可用 / 已经上线” → 实际是单机 Compose 验证；
- ❌ “多 Agent 架构” → 实际是单 Agent + 工具注册表；
- ❌ “用了 RAG / 向量数据库” → 没有；
- ❌ “真实模型准确率 76/90” → 76/90 是离线后验，as-run 是 69/90；
- ❌ “所有超时都能在 120s 内结束” → 修复只证明清理不阻塞，未在真实停顿复验；
- ❌ “密钥已安全轮换” → 那是用户声明，不是技术验证；
- ❌ 把脚本化假客户端的测试结果说成真实模型结果。
